# Мультиклиентские сборки календаря

Дата: 2026-07-30

Спека лежит в `specs/`, а не в `docs/superpowers/specs/`, потому что `docs/`
публикуется GitHub Pages и любой файл оттуда уезжает на боевой адрес.

## Задача

Сейчас в репозитории один календарь по адресу
`https://yaroslavmalygin.github.io/bc-2026-1/`. Нужно уметь заводить календарь
на каждого нового клиента астролога по отдельной ссылке, без копирования
проекта и без ручной правки кода.

Клиенты различаются:

- **диапазоном** — год считается не всегда с августа: бывает сентябрь→сентябрь,
  ноябрь→ноябрь. Значит 12 или 13 месяцев, 365–396 дней;
- **набором строк** — кому-то не нужен массаж, но нужна пластика и операции.
  Число строк обычно восемь, но не гарантировано;
- **набором символов** — под новые строки астролог может ввести новые буквы.

Структура, цвета и расположение текстов одинаковы у всех.

## Что уже готово и менять не надо

Разведка по коду показала, что приложение почти не привязано ни к адресу, ни к
конкретному клиенту:

- пути везде относительные (`./`), service worker регистрируется относительно,
  `scope` в манифесте `./`;
- `docs/validate.js` выводит ожидаемые месяцы и дни **из `range.start` и
  `range.end`**, строки читает из `data.rows` с произвольными id и количеством;
- `docs/app.js` считает компактный режим по `state.rows.length`;
- в `styles.css` захардкоженного числа строк нет, восемь строк делят высоту
  через `flex: 1 1 0`.

Захардкожено ровно в двух местах, оба в конвертере: `RANGE_START` / `RANGE_END`
/ `EXPECTED_MONTHS` / `EXPECTED_DAYS` и `ROW_DEFS` в `tools/calendar_config.py`.

## Ключевой риск: общий origin

Все страницы GitHub Pages этого аккаунта живут на одном origin
`yaroslavmalygin.github.io`. Cache Storage, IndexedDB и localStorage делятся
**по origin, а не по пути**. Три идентификатора сейчас глобальные:

| Где | Что | Чем грозит |
|---|---|---|
| `store.js` | `DB_NAME = "business-calendar"` | два календаря на одном устройстве пишут в одну базу — офлайн покажет чужие данные, молча |
| `sw.js` | `calendar-shell-v1` | `activate` удаляет всё, что `startsWith("calendar-shell-")`, — подъём версии у одного клиента сносит офлайн-оболочку остальных |
| `manifest.webmanifest` | `"id": "/bc-2026-1/"` | одинаковый id мешает установке нескольких календарей |

Это тихая поломка: приложение офлайновое, ошибку никто не заметит месяцами.
Изоляция обязана быть покрыта тестом, а не аккуратностью.

## Принятые решения

### Публичность

Репозиторий остаётся публичным, папки клиентов видны на GitHub. Решение
осознанное: календарь уникален под заказчика и чужому бесполезен. Отсюда
следует, что случайные слаги не нужны — клиент опознаётся **порядковым
номером**, он же папка, он же адрес: `…github.io/bc/01/`.

Обязательное условие: ни имён, ни персональных данных нигде. Существующий
механизм `PRIVACY_STOPWORDS` остаётся как есть; дополнительного сторожа не
строим — контроль за именами берёт на себя Яро, для этого в воркфлоу есть шаг
показа всех заметок месяцев до публикации.

### Хостинг

GitHub Pages, как сейчас. Проверено по документации: сайт Pages доступен всему
интернету даже из приватного репозитория, закрытая публикация есть только в
GitHub Enterprise Cloud. Приватность здесь всё равно не покупается, а
публичность нас устраивает.

### Репозиторий

`bc-2026-1` переименовывается в `bc`. Момент удачный: боевая ссылка ещё никому
не передана.

## Архитектура

### Структура

```
app/                  исходник оболочки, бывшее содержимое docs/
  index.html  styles.css  fonts.css  app.js  dates.js
  moon.js  store.js  validate.js  sw.js
  manifest.webmanifest  icons/  OFL.txt

clients/
  01/
    client.json       коммитится: диапазон, строки, доп. символы
    calendar.xlsx     .gitignore, исходник астролога
  02/ …

docs/                 публикуется GitHub Pages
  .nojekyll  robots.txt        общие на весь сайт, правятся руками
  01/  02/ …                   генерируются целиком, руками не трогаются

tools/build_client.py
workflows/add_client.md
```

Разделение «исходник → сборка» существенно: без него `docs/` был бы
одновременно и источником правды, и результатом, и пересборка клиентов
затирала бы то, что правили.

На голом `…github.io/bc/` — ничего, 404. Оглавление со списком клиентов было бы
ровно тем перечислением, которого мы избегаем.

### Изоляция клиентов

Идентификатор клиента **выводится из адреса скрипта**, а не подставляется
генератором:

- `sw.js`: `new URL("./", self.location.href)` → `/bc/01/` → последний непустой
  сегмент `01`;
- `store.js`: `new URL("./", import.meta.url)` → то же самое.

Берём адрес **скрипта**, а не документа: от документа идентификатор поехал бы
при другом имени входной страницы.

Отсюда:

- `DB_NAME = "business-calendar-01"`;
- `CACHE_NAME = "calendar-01-shell-v1"`, и чистка в `activate` фильтрует по
  **своему** префиксу `calendar-01-shell-`, а не по общему;
- поиск в кэше делается внутри своего кэша (`caches.open(CACHE_NAME)` →
  `cache.match`), а не глобальным `caches.match` по всем кэшам origin.

Рассинхрон «папка `02`, идентификатор `01`» становится невозможен по
построению.

Если сегмент пуст (локальный сервер над самой папкой клиента), идентификатор
равен `local`.

### Манифест — единственный шаблонизируемый файл

`"id": "./"` **не подходит**. Проверено по документации: `id` резолвится
относительно origin, а не папки, поэтому `./`, `foo`, `/foo` и `../foo` дают
один и тот же идентификатор — у всех клиентов он совпал бы.

Генератор пишет явный абсолютный `id`: `/bc/01/`. Вариант «убрать `id`, он
подставится из `start_url`» рабочий, но опирается на умолчание, которое
браузерным тестом не проверить; для проекта с такими инвариантами явное лучше.

### Конфиг клиента

`clients/NN/client.json`:

```json
{
  "range": { "start": "2026-09-01", "end": "2027-09-30" },
  "rows": [
    { "id": "negotiations", "label": "Важные переговоры и выступления", "short": "Переговоры" },
    { "id": "surgery", "label": "Пластика, операции", "short": "Операции" }
  ],
  "extraMarks": { "П": "Расшифровка новой буквы." }
}
```

Из `calendar_config.py` уезжают `RANGE_START`, `RANGE_END`, `ROW_DEFS`.
`EXPECTED_MONTHS` и `EXPECTED_DAYS` **вычисляются из диапазона**: сейчас это три
независимые константы, которые можно рассогласовать, после переезда
противоречить нечему. `ACTIVITY_ROW_COUNT` становится `len(rows)`, расхождение
с таблицей останавливает конвертер.

Глобальным остаётся всё, что про астролога, а не про клиента: обе палитры,
раскладка блока месяца, каталог `KNOWN_MARKS` с расшифровками, имена месяцев,
стоп-слова, `PROVISIONAL_PALETTE`, пороги фаз луны.

`extraMarks` **дополняет** каталог, не заменяет: неизвестная буква по-прежнему
останавливает сборку, пока её осознанно не впишут.

### Генератор

`tools/build_client.py NN` — копирование `app/` → `docs/NN/` плюс манифест с
подставленным `id`. Флаг `--all` пересобирает оболочку у всех клиентов: он
нужен после любой правки приложения, вместе с подъёмом `APP_CACHE_VERSION` в
`app/sw.js`.

**Оболочка и данные разделены.** `build_client.py` собирает только оболочку и
**сохраняет существующий `docs/NN/data/calendar.json` нетронутым**. Данные
пишет исключительно конвертер, отдельным шагом. Иначе `--all` на машине без
`.xlsx` (он под `.gitignore`, значит на чистом клоне его нет) стёр бы данные
всех клиентов разом — при том что офлайновое приложение показало бы это не
сразу.

Список клиентов для `--all` берётся из `clients/`, а не из `docs/`: источник
правды — вход, а не результат.

`.gitignore` пополняется `clients/*/*.xlsx`.

Цена самодостаточной папки — около 230 КБ на клиента в git, из них 79 КБ шрифт.
Общая оболочка на всех сэкономила бы место, но правка общего кода тихо меняла бы
поведение у всех клиентов без пересборки и без прогона тестов на их данных — для
офлайнового приложения это шаг назад.

## Воркфлоу «заводим клиента»

`workflows/add_client.md`:

1. **Номер** — следующий свободный в `clients/`.
2. **Интервью**: диапазон (первый и последний месяц); набор строк — показываю
   текущие восемь, Яро говорит, что убрать и что добавить; известны ли новые
   буквы. Пишу `clients/NN/client.json`.
3. **Яро кладёт `calendar.xlsx`** в `clients/NN/`.
4. **Сверка палитры** — `--report-colors`, пока `PROVISIONAL_PALETTE` не снят.
5. **Холостой прогон** конвертера в `.tmp`, не в `docs/`.
6. **Сверка символов с каталогом**: конвертер печатает все встреченные буквы и
   помечает отсутствующие в `KNOWN_MARKS`. Новые вписываются в `extraMarks` с
   расшифровкой из легенды таблицы, по одной.
7. **Показ заметок месяцев** целиком, до публикации — шаг контроля по именам.
8. **Сборка** `docs/NN/` и прогон всех тестов.
9. **Коммит, пуш**, затем `test_live.mjs` по адресу клиента.
10. Ссылка передаётся Яро.

`workflows/update_calendar_data.md` переписывается под «клиент NN» — это путь,
когда астролог присылает исправленную таблицу уже заведённому клиенту.
Пересборка всех после правки приложения — одна команда `build_client.py --all`,
отдельного воркфлоу не требует.

## Тесты

- **`test_dates.mjs`** — импорт `docs/dates.js` → `app/dates.js`.
- **`test_app.mjs`** — вместо сервера над `docs/` поднимается сервер над
  тестовой сборкой: фикстура `tests/fixtures/client-test.json` плюс демо-книга
  собираются в `.tmp/build/`. Тесты перестают зависеть от наличия живого
  клиента. Сервер поднимается над `.tmp/build/`, клиент лежит в подпапке —
  иначе сегмент пути пуст и идентификатор не проверить по-настоящему.
- **`test_converter.py`** — 16 сломанных книг гоняются против фикстуры. Плюс три
  новых случая: диапазон таблицы не совпал с `client.json`, число строк не
  совпало, встретилась буква не из каталога и не из `extraMarks`.
- **`test_clients.mjs`, новый** — собираются два клиента с разными данными и
  открываются в одном браузерном профиле. Проверяется: базы IndexedDB разные,
  кэши разные, данные не перетекают, подъём `APP_CACHE_VERSION` у одного не
  сносит офлайн-оболочку другого.
- **`test_live.mjs`** — меняется адрес по умолчанию.

## Миграция первого клиента

- `docs/*` → `app/`, кроме `.nojekyll` и `robots.txt`;
- `clients/01/client.json` с текущим диапазоном `2026-08-01 … 2027-08-31` и
  нынешними восемью строками;
- сборка `docs/01/` на демо-данных с плашкой «предварительные», как сейчас;
- репозиторий `bc-2026-1` → `bc`, живой адрес `…github.io/bc/01/`;
- `CLAUDE.md` и `README.md` пополняются двумя инвариантами: идентификатор
  выводится из адреса скрипта; диапазон и строки живут в конфиге клиента.

У Яро и астролога в браузере остаётся зарегистрированный service worker на
старом адресе. Он не мешает, но живёт своей жизнью — стоит один раз удалить
сайт с домашнего экрана и почистить данные сайта.

## Вне рамок

- Подтверждение палитры: `PROVISIONAL_PALETTE` снимается отдельно, когда придёт
  настоящий `.xlsx`.
- Оглавление по клиентам, авторизация, приватность содержимого.
- Персонализация оформления: структура, цвета и расположение текстов у всех
  одинаковы.
