# Обновление данных календаря

SOP на случай, когда астролог сдал новый год или поправил месяц **уже
заведённому** клиенту. Занимает пять минут, из которых четыре — это шаг 6,
и пропускать его нельзя.

Клиента ещё нет — см. [add_client.md](add_client.md).

## Что понадобится

- Номер клиента `NN` (папка в `clients/`)
- Таблица этого клиента в Google Sheets, выгруженная в `.xlsx`
- Телефон с установленным приложением

---

## 1. Выгрузить таблицу

В Google Sheets: **File → Download → Microsoft Excel (.xlsx)**.
Положить файл в `clients/NN/calendar.xlsx`.

> Только `.xlsx`. CSV, PDF и любой текстовый экспорт теряют заливку ячеек,
> а в ней половина смысла календаря — благоприятность дня и фазы луны.

## 2. Посмотреть, какие цвета в файле

```bash
python tools/xlsx_to_calendar_json.py \
  --xlsx clients/NN/calendar.xlsx \
  --client clients/NN/client.json \
  --report-colors
```

Отчёт показывает все встреченные заливки, их вид (обычный RGB, цвет темы,
индексированный) и к какой корзине они отнесены.

Что проверить:

- **Нет строк «НЕ ОПИСАН В ПАЛИТРЕ».** Появились — значит в таблице новый
  оттенок. Либо заменить его в таблице на уже используемый, либо добавить
  в `PALETTE_ACTIVITY` или `PALETTE_DATES` в `tools/calendar_config.py`.
- **Вид заливки — `rgb`.** Если встретился `theme`, конвертер его разберёт,
  но стоит убедиться, что цвета не поехали.
- **Условного форматирования нет.** Конвертер остановится сам, если правило
  задевает календарные данные: `openpyxl` не видит цвет, созданный правилом,
  и календарь вышел бы обесцвеченным.

## 3. Прогнать конвертер

```bash
python tools/xlsx_to_calendar_json.py \
  --xlsx clients/NN/calendar.xlsx \
  --client clients/NN/client.json \
  --out docs/NN/data/calendar.json
```

Любое расхождение останавливает работу с указанием месяца и ячейки. Это
задумано: приложение офлайновое, и тихо испорченные данные никто не заметит
месяцами.

Если астролог заодно изменил набор строк или диапазон — сначала правится
`clients/NN/client.json`, иначе конвертер остановится на расхождении
«таблица против конфига». Это и есть его работа.

Сдвинулся диапазон — обязательно переспросить и **опоры луны**
(`moonAnchors`): ближайшую фазу до нового начала и после нового конца.
Старые опоры окажутся не соседними, и конвертер это скажет.

## 4. Пройти шлюз перед публикацией

Конвертер печатает его сам в конце. Публиковать как **финальную** версию
календаря можно, только когда все строки зелёные:

- все месяцы диапазона имеют статус `READY`
- дней ровно столько, сколько объявляет конфиг клиента
- разрывов в фазах нет
- палитра подтверждена по реальному `.xlsx` (`PROVISIONAL_PALETTE = False`)
- `dataHash` рассчитан

Пока `provisional: true`, приложение честно показывает плашку
«Предварительные данные», и это не финальный календарь.

**Статусы месяцев.** Заполненность определяется маркером `STATUS: READY`
в колонке **A**, в той же строке, где заголовок месяца в колонке B. Нет
маркера — месяц считается незаполненным, и приложение вместо строк напишет
«Данные на этот месяц ещё не заполнены». Соврать данными другого месяца оно
не может по построению.

## 5. Прогнать тесты

```bash
python tests/test_client_config.py   # конфиг клиента
python tests/test_build_client.py    # генератор сборок
python tests/test_converter.py       # 19 сломанных книг
node   tests/test_dates.mjs --all-zones
node   tests/test_client_id.mjs      # идентификатор из адреса
node   tests/test_app.mjs            # приложение в браузере
node   tests/test_clients.mjs        # изоляция двух клиентов
```

## 6. Решить, менять ли версию оболочки

Два независимых механизма, и путать их нельзя:

| Что изменилось | Что делать |
|---|---|
| только `docs/NN/data/calendar.json` | **ничего**, версия подхватится из `dataHash` |
| разметка, скрипты, стили, шрифт, иконки, манифест, `sw.js` | поднять `APP_CACHE_VERSION` в `app/sw.js`, затем `python tools/build_client.py --all` |

Правка в `app/` сама по себе никому не доезжает: клиенту раздаётся его копия
в `docs/NN/`. Без пересборки изменится только исходник.

`--all` перекладывает оболочку и **не трогает** `docs/NN/data/`: данные пишет
только конвертер.

## 7. Опубликовать

```bash
git add -A
git commit -m "Обновлены данные календаря клиента NN"
git push
```

GitHub Pages подхватит изменения за минуту-две.

## 8. Проверить с иконки на телефоне

Открыть приложение **с домашнего экрана**, а не во вкладке браузера, и
убедиться, что данные новые.

Это не формальность. Всё, что тихо ломается при обновлении, ломается именно
между шагами 7 и 8: приложение в браузере и установленное приложение —
разные экземпляры, и поведение кэша у них может отличаться.

Затем включить авиарежим и открыть снова: должно работать на сохранённой
копии.

## Если что-то пошло не так

**Конвертер остановился.** Прочитать сообщение: там указан месяц и ячейка.
Все проверки написаны так, чтобы говорить, что именно не сошлось, а не
«ошибка разбора». Разбор типичных случаев — в
[add_client.md](add_client.md#если-конвертер-остановился).

**Приложение показывает старые данные.** Проверить, что `dataHash` в новом
`docs/NN/data/calendar.json` действительно отличается от прежнего. Затем — что
GitHub Pages уже задеплоил новый файл (вкладка Actions в репозитории).

**Приложение говорит «Получены повреждённые данные».** Значит новый JSON не
прошёл проверку, и приложение осталось на последней рабочей версии — так и
задумано. Причина пишется в консоль браузера.

**У клиента пропали офлайн-данные.** Скорее всего поехал номер папки: имя
базы и префикс кэша выводятся из адреса. Клиент, переехавший с `/bc/01/` на
`/bc/02/`, для браузера — другое приложение. Номер после выдачи ссылки
не меняют.

**Нужно откатиться.** `git revert` последнего коммита и `git push`. Телефон
подхватит откат тем же путём.
